# Enterprise Custom Domain Module — Audit (pre-implementation)

Date: 2026-08-07. Read-only audit, no code changed. Scope: existing custom-domain feature (schema, controllers, routing) and readiness for a driver-based architecture (shared-hosting / VPS+Nginx / VPS+Caddy) where DB and UI never change when the driver changes.

## 0. Executive summary

**No driver abstraction of any kind exists today.** A repo-wide search for `VPSDriver`/`NginxDriver`/`CaddyDriver`/`ShareDriver`/`SharedDriver`/`DomainDriver`/`DomainManager` returns nothing — this is a greenfield build, not a refactor.

**More importantly: the existing custom-domain feature is currently a complete no-op in production.** The DB schema, the tenant-facing request form, and the super-admin approve/reject screen are all fully built — but nothing at the routing layer ever acts on an approved domain while `TENANCY_MODE=path` (the current production mode). A tenant can request a domain, staff can approve it, the UI will proudly show "🌐 সক্রিয় কাস্টম ডোমেইন," and a real visitor hitting that domain gets nothing from this app — not even a 404, since no route in path mode is unconstrained by `Route::domain(config('app.central_domain'))`. This needs to be understood before any "enterprise" work is designed on top of it.

## 1. Current implementation, traced end-to-end

- **Schema** (`database/sql/schema.sql:37-38,53` + `chunk12.sql`): `tenants.custom_domain` (unique), `custom_domain_verified` (bool), `custom_domain_requested`, `custom_domain_request_status` (none/pending/approved/rejected). Schema comment literally says `-- myshop.com (Phase 3)`, confirming this was always known to be an incomplete, staged feature.
- **Plan gating**: `plans.allow_custom_domain` — only the top-tier plan has it (`chunk10.sql:14`), checked in `SettingController::requestDomain`.
- **Tenant-facing flow** (`SettingController::requestDomain`, `resources/views/tenant/settings.blade.php`): tenant types a domain string, regex-validated as domain-shaped, saved as `custom_domain_requested` + status `pending`. No DNS instructions shown to the tenant at all — no "add this CNAME/A record" guidance anywhere in the UI.
- **Approval flow** (`SuperAdmin\TenantController::approveDomain`/`rejectDomain`, `resources/views/super/tenant-show.blade.php`): a human staff member clicks Approve. This **blindly copies the tenant-typed string into `custom_domain` and sets `custom_domain_verified = 1`** — zero DNS ownership check, zero automated verification of any kind. It is trust-the-tenant, not verify-the-tenant.
- **Routing** (`app/Http/Middleware/ResolveTenant.php`): two code paths.
  - `resolveByPath()` — active in production today (`TENANCY_MODE=path`) — resolves purely via `/shop/{tenant_slug}`. **Never reads `custom_domain` at all.**
  - `resolveBySubdomain()` — only reached when `TENANCY_MODE=subdomain` — this is the one path that actually checks `Tenant::where('custom_domain', $host)->where('custom_domain_verified', true)`. And even here, no re-verification ever happens after the initial manual approval — if DNS is later pointed elsewhere, the flag stays `verified` forever with no expiry/recheck.
  - Confirmed by `routes/web.php:289-297`: in path mode, tenant routes are wrapped in `Route::domain(config('app.central_domain'))`, so a request arriving on `myshop.com` doesn't match any route group in this app at all. In subdomain mode, the tenant route group has no domain constraint, so `resolveBySubdomain()` is reached for any host and does the real lookup.
  - `Tenant::url()` (`app/Models/Tenant.php:53-64`) confirms this isn't an oversight: it explicitly returns the `/shop/{slug}` URL in path mode regardless of `custom_domain_verified`, and only builds a `https://{custom_domain}` URL in subdomain mode.
- **No SSL/TLS automation anywhere.** No certbot, ACME client, Let's Encrypt package, or any TLS-provisioning code in the repo (verified by grep — the only `ssl`-matching hits are the unrelated SSLCommerz payment gateway).
- **No webserver/vhost automation anywhere.** `deploy.sh` has zero awareness of custom domains — it's a single rsync into one shared app directory. Hostinger shared hosting (the current host) would require a human to add each custom domain as a cPanel "Addon"/"Parked" domain pointing at the same docroot for the Host header to even reach this app in the first place — nothing in this repo does or could do that today without cPanel/WHM API credentials, which haven't been referenced anywhere in the codebase or `.env.example`.

## 2. Findings (current state, before any new module is built)

| Severity | Finding | Impact | Fix direction | Effort |
|---|---|---|---|---|
| 🔴 Critical | Custom domains don't route at all in the active production mode (`TENANCY_MODE=path`) — the entire feature is currently cosmetic. | Any tenant who's had a domain "approved" believes it's live; it isn't. Support burden, trust damage the day a merchant tells customers to visit their domain and it fails. | This is the central problem the new module needs to solve — see open questions below, since the right fix depends on whether shared-hosting support is in scope or this waits for VPS migration. | Depends on scope decision. |
| 🔴 Critical | Zero DNS ownership verification before a domain is marked `verified`. Approval is 100% "staff trusts what the tenant typed." | Even once routing is fixed, nothing stops a tenant claiming a domain they don't control, or (worse, under subdomain mode where routing does work) two tenants racing to claim the same unverified string before a real check exists. | Automated DNS verification (TXT record or CNAME-to-a-unique-token check) before any driver provisions/activates a domain — this part is hosting-environment-independent and worth building regardless of the driver decision. | Not estimating yet — folds into module design. |
| 🟠 High | No SSL/TLS provisioning of any kind. Even in subdomain mode where routing works, a verified custom domain has no certificate — browsers show security warnings or the site fails to load over HTTPS entirely, depending on how DNS/hosting is configured outside this app. | Broken/insecure storefront experience for any tenant who successfully gets this far. | Driver-specific: Caddy auto-provisions TLS on domain add with no separate step; Nginx+VPS needs a certbot/ACME integration; shared hosting likely depends on host-level AutoSSL (cPanel) which this app has no visibility into today. | Depends on driver scope. |
| 🟡 Medium | No webserver-level automation — approving a domain in the DB doesn't make any webserver actually listen for it. On shared hosting this requires an out-of-band manual step (cPanel addon domain) that isn't documented anywhere. | Even a "fixed" routing layer + DNS verification doesn't make the domain reachable unless someone separately configures the webserver — a gap between "approved in the app" and "actually working." | The driver abstraction itself is the fix — a shared-hosting driver should probably surface this as a manual instructional step to staff rather than pretend to automate what it can't. | Depends on driver scope. |
| 🟡 Medium | No re-verification/expiry of an approved domain — DNS can be repointed away after approval and the app never notices. | Silent breakage indistinguishable from "still working" in the admin UI. | Periodic re-check (scheduled command) once DNS verification exists at all. | S once verification exists. |
| 🟢 Low | Tenant-facing UI gives no DNS setup instructions (no "point a CNAME to X" guidance). | Tenants who don't already know how DNS works have no path to self-serve; every request likely needs manual support back-and-forth. | Add clear instructions once the target architecture (and thus the correct DNS records to advertise) is decided. | XS once the architecture is fixed. |
| 🟢 Low | No audit trail — who approved/rejected a domain and when isn't recorded beyond the tenant's own `updated_at`. | Minor — hard to audit history of domain changes later. | Add timestamps/actor columns if/when this matters. | XS. |

## 3. Architecture precedent already in this codebase

This project already has a working, idiomatic version of exactly the pattern requested — `app/Services/Courier/CourierManager.php`. It's a `*Manager` static factory keyed off a DB-stored `provider` string, returning `null` when a given provider's required credentials aren't present, with each provider's actual logic isolated in its own class (`SteadfastService`, `PathaoService`) behind an implicit shared contract. PROJECT_KNOWLEDGE.md already lists this as a "confirmed good" pattern.

**Recommendation: mirror this shape exactly for the domain module** — a `DomainManager` + a `DomainDriver` interface (`verify()`, `provision()`, `deprovision()`, `status()`), with `ShareDriver`/`NginxDriver`/`CaddyDriver` implementations selected by a config value (e.g. `config('domains.driver')` / env `DOMAIN_DRIVER`), the same way `TENANCY_MODE` already switches `ResolveTenant`'s behavior. This satisfies "DB and UI never need to change when switching drivers" the same way `CourierManager` already lets the Settings UI stay identical regardless of which courier is active.

## 4. Open questions before a design/effort estimate can be finalized

These are product/infrastructure decisions, not code questions — I can't responsibly size the work without them:

1. **Is shared-hosting custom-domain support actually in scope now**, or is this module meant for the post-VPS-migration world CLAUDE.md already describes ("subdomain mode... after moving to VPS")? Building real shared-hosting support means either getting cPanel/WHM API access for this Hostinger account, or accepting that the "shared driver" is instructional-only (tells staff what to do by hand) rather than automated.
2. **Does the current Hostinger plan expose any cPanel/WHM API token?** If not, `ShareDriver` can realistically only do DNS verification (pure PHP, no server access needed) and generate setup instructions — it cannot add addon domains or provision SSL on its own.
3. **For the future VPS phase, is the target Nginx+certbot or Caddy?** Caddy is materially simpler for this exact feature (automatic per-domain TLS with no separate certbot scripting) — worth deciding explicitly now if no VPS provider/stack decision has been made yet, since it changes how much of `NginxDriver` vs `CaddyDriver` is worth building first.
4. **Should this module ship in phases** — e.g., Phase 1 = automated DNS verification only (works today, hosting-independent, immediately closes the "approval is just trust" gap) before Phase 2 = actual driver-based provisioning once the VPS/hosting-access questions above are answered?

I'd like your direction on these before proposing a concrete implementation plan and effort estimate, per your "report first, wait for approval" instruction — the effort number changes by an order of magnitude depending on the answers.
