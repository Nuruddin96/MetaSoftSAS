# ShopSaaS — Product Quality & Enterprise Readiness Audit

Date: 2026-08-07. Read-only audit, no code changed. Covers: security/auth, data integrity/business logic, reliability/operations, testing & deployment, performance/scalability, and the recently-redesigned marketing site + tenant panel (code-quality/accessibility only — visual design was explicitly out of scope and is not touched or critiqued here).

This supersedes and re-verifies every item in `PROJECT_KNOWLEDGE.md` §7 against current code (much has changed since that audit: the product gallery feature, the deploy pipeline rewrite, and both redesign phases). Prior item numbers (7.x) are cross-referenced where they still apply.

**Nothing in this document has been fixed. This is a punch list only, pending your approval per phase.**

## 🔴 Critical

| # | Issue | Impact | Recommended fix | Effort |
|---|---|---|---|---|
| **C1** | Live production `APP_KEY` and mail credentials (`MAIL_PASSWORD`, `MAIL_HOST`, `MAIL_USERNAME`) are committed to git as `.env.save` / `.env.save.1`, not covered by `.gitignore`. The `APP_KEY` is byte-identical to the real production key. | Anyone with current or historical repo read access can decrypt every `encrypted`/`encrypted:array` DB field (courier API keys, Messenger tokens, Meta CAPI secrets) and forge valid session cookies for all 4 auth guards (tenant/super_admin/affiliate/web). Also the precondition that turns H1 (stored XSS) from "a bug" into "any staff member can attack your storefront visitors." | Role-based Policy/Gate or a `role:owner,manager` middleware on sensitive route groups (Settings, Billing, destructive deletes) at minimum; full per-route role matrix ideally. | M (1–2 days) — mostly mechanical once the role matrix is decided, but needs a decision pass on which of the ~40 panel routes each role should reach. |

Add a post-rsync `curl` health check to `deploy.sh` that aborts/alerts on non-200, and add the missing `artisan migrate --force` step. | CI workflow: S (few hrs). `deploy.sh` health check + migrate step: S (half day). Writing a real feature-test suite: XL, ongoing — not a blocker for the above two. |

## 🟠 High

| # | Issue | Impact | Recommended fix | Effort |
|---|---|---|---|---|
| **H1** | `resources/views/storefront/page.blade.php` renders custom page content with raw `{!! $page->content !!}` — no HTML sanitizer on save (`WebsiteController::storePage`/`updatePage` only validate `string|max:50000`). | Combined with C3: any tenant staff member (not just the owner) can inject `<script>` into a public About/Privacy/custom page that runs for every anonymous storefront visitor — session/cookie theft, checkout phishing overlays. New since the page-builder feature; the one raw-output spot in the whole view tree. | Sanitize on save with an HTML purifier (allowlist-based), or strip tags entirely if these pages don't need rich HTML. | S (few hrs — add purifier package + wrap the save path). |
| **H2** | No login throttling on any of the 3 login forms (Tenant/SuperAdmin/Affiliate). (PK §7.12, confirmed still open.) | Brute-force against any known email is currently unmitigated on all 3 guards. | `throttle:5,1` middleware on the 3 login POST routes. | XS (<1hr). |
| **H3** | `MessengerWebhookController::receive()` never validates `X-Hub-Signature-256` against the Meta app secret; page ownership resolves purely from attacker-controlled `entry[].id`. (PK §7.13, confirmed still open.) | A forged POST naming a real connected `page_id` can inject fake messages into a tenant's Messenger inbox. | Verify HMAC-SHA256 of the raw body before processing, reject on mismatch. | S (1–2hrs). |
| **H4** | `BillingController::bkashCallback`/`sslCallback` guard against reprocessing with a check-then-act `if ($payment->status === 'completed') return` — not wrapped in a transaction or `lockForUpdate()`. | A duplicate callback (gateway retry, browser refresh racing the webhook) can pass the check twice before either `update()` lands, double-activating a subscription and double-crediting the affiliate's one-time 20% commission. Real money impact, newly found — not in the prior audit. | Wrap `activateSubscription()` in `DB::transaction()` with `lockForUpdate()` on the payment row, or convert to an atomic conditional `UPDATE ... WHERE status='pending'` and only proceed if rows-affected > 0. | S (2–4hrs, needs careful testing given it's payment-critical). |
| **H5** | No stock-availability check before `Inventory::decrement()` in any of the 3 order-creation paths (Order/POS/Checkout), no DB-level `CHECK` constraint. (PK §7.6, confirmed still open.) | Concurrent sales of the last unit, or a manual order exceeding stock, can drive inventory negative with no error. | `lockForUpdate()` + explicit availability check inside the transaction before decrementing, rollback with a friendly error if insufficient. | M (half–1 day across 3 controllers, plus consistent UX messaging). |
| **H6** | `OrderController::bulkCourier` catches courier-dispatch failures with `catch (\Throwable $e) { $failed++; }` — no `Log::error`, no `report()`, exception is never inspected. All courier/payment/messenger service classes themselves have zero error logging; it lives only (inconsistently) at call sites. | If a courier credential expires or an API contract changes, bulk dispatch fails silently in aggregate — the merchant sees a bare failure count with zero diagnostic trail to investigate. | Add `Log::error()`/`report($e)` in the catch block at minimum; consider standardizing error logging inside the service classes themselves. | XS (30 min for the immediate fix). |
| **H7** | `QUEUE_CONNECTION=database` is configured and `queue:listen` runs in local dev, but zero `App\Jobs\*` classes exist and zero `dispatch()` calls exist anywhere. All courier/fraud-check/Messenger/SMS/payment API calls run synchronously in the request cycle — including `bulkCourier`, which loops them per order (could exceed shared-hosting `max_execution_time` on a large batch). Worse: no scheduler, no Supervisor/systemd config, and no crontab reference exists anywhere in the repo — **if jobs were added today, nothing in production would actually process them.** (PK §7.9, confirmed open, compounded.) | Slow/down third-party APIs currently block the request thread directly (checkout, bulk courier actions). Fixing "sync calls" requires first confirming Hostinger shared hosting can even run a persistent queue worker or cron-driven `queue:work --stop-when-empty` — this needs a hosting-capability check before implementation, not just code. | Add `App\Jobs\*` classes for courier dispatch/fraud check/Messenger send/SMS, `dispatch()` them from call sites; separately, confirm/configure a cron-driven queue runner on the host (likely `* * * * * php artisan queue:work --stop-when-empty` via cPanel cron, not a long-running process). | L (2–4 days — code portion is moderate, but hosting-capability discovery could add delay outside our control). |
| **H8** | `InventoryController::lowStock()` runs `ProductVariant::with(['product','inventory'])->get()` with no `where` and no pagination — loads every variant for the tenant, filters in PHP. | Will get slow/memory-heavy as a tenant's catalog grows; already the one real pagination gap found (every other list view correctly paginates). | Push the low-stock filter into SQL (same `HAVING` pattern already used in `DashboardController`) and paginate. | S (2–3hrs). |
| **H9** | Accessibility: every `<img>` in the tenant panel (product thumbnails, gallery, product-source images, website banners/logo) is missing `alt` entirely — the landing page already handles this correctly, the panel redesign didn't carry the pattern over. Also: icon-only stepper/delete buttons with no `aria-label`, several form inputs relying on placeholder-only text with no `<label>`/`aria-label` (search, courier credentials, POS due-sale fields, inventory adjust). | Screen-reader users get no context on product images or icon-only controls; placeholder-only inputs fail WCAG 3.3.2. Real UX harm for any visually-impaired staff/merchant. | Mechanical sweep: add `alt="{{ $product->name }}"` (or `alt=""` for decorative), `aria-label` on icon buttons, visually-hidden `<label>` or `aria-label` on placeholder-only inputs. Explicitly NOT a redesign — pure additive-attribute fix, no visual change. | S (few hrs, mechanical). |

## Recommended implementation order

Ordered by a mix of severity, dependency, and effort-to-risk ratio — not strictly severity-sorted, since some Critical items (like the queue/hosting question inside H7) take longer to derisk than some High items that are quick wins.

**Phase 0 — Emergency, independent of everything else (do first, today):**
C1 (rotate `APP_KEY`/mail password, purge git history, fix `.gitignore`). This is a live exposure, not a backlog item — treat it separately even before you approve the rest of this report.

**Phase 1 — Stop the bleeding (data-loss & production-safety floor):**
C2 (backup + delete-confirmation gate), C4 (minimal CI + deploy health check + missing migrate step). These are cheap relative to their blast-radius reduction and don't depend on anything else here.

**Phase 2 — Close the authorization gap:**
C3 (role enforcement). Do this before H1 (XSS) — C3 is the precondition that makes H1 exploitable by "any staff member" rather than just the owner, so narrowing who can reach Settings/Website-editing first shrinks H1's blast radius even before H1 itself is patched.

**Phase 3 — High-severity security & money correctness:**
H1 (XSS sanitize), H2 (login throttling), H3 (webhook signature), H4 (billing race), H5 (stock guard), H6 (bulkCourier logging — trivial, bundle in). These are mostly independent, quick-to-medium fixes with real exploit/money impact.

**Phase 4 — Reliability foundation:**
H7 (queue infrastructure + hosting-capability check) and its bundled cleanup M7 (scheduled pruning). Flagging this as its own phase since it needs a hosting-capability discovery step before code, unlike everything above.

**Phase 5 — Performance & scale:**
H8 (paginate low-stock), M5 (dashboard caching), M6 (thumbnails), M9 (indexes), M10 (orphaned file cleanup).

**Phase 6 — Correctness cleanup & consistency:**
M1+M2 (warehouse_id + OrderService extraction, do together since M2 is the root cause), M8 (coupon decision — needs your call), M3/M4 (session cookie + rate limiting, quick), M11 (design-system gap-filling — needs your explicit go-ahead given the "don't touch design" line), M12 (fillable allowlists), M13/M14 (onboarding docs), M15 (POS receipt popup).

**Phase 7 — Low-priority polish:**
L1–L9, batched together as a single cleanup pass since none are urgent and most are XS effort.
